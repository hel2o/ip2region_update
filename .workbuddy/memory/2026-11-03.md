# 2026-11-03

## ip2region 归属库重写（阶段 0 完成）

**目标**：qqwry.dat → ip2region xdb，用百度 API 提升省市/ISP 精度，叠加自定义 CIDR 覆盖。
输出区域串 6 段：`国|省|市|区|镇|ISP`（示例 `中国|广东省|广州市|番禺区|钟村|中国电信`）。

### 关键结论
- 百度 opendata 接口 `https://opendata.baidu.com/api.php?query=<ip>&co=&resource_id=6006&oe=utf8`
  免费、无 AK、无配额限制；实测 30 并发 2 秒全 200。返回 `data[0].location` = `<省市连写> <ISP>`。
  **只到城市级**（偶尔到区，如百度自己的 IP），**给不出区镇**。
- 因此：区/镇 100% 来自 qqwry；百度只用于纠正省市 + 校验 ISP。
  反面教材 = 旧 `ip2region.go` 的"API 查不到就整段覆盖"，会把区镇抹空。
- `北京市北京市` 这类省市重复、`广东省深圳市 电信` 这类省市连写，必须有行政区划字典做最长前缀切分（阶段 3）。
- region 是 6 段，官方 SDK 的 `Region` 按 5 段解析，**查询侧不能直接用官方便捷方法**。

### 架构决策
- 运行形态：单机 + SQLite（段表 / ip_cache / overrides），断点续跑 + 重跑零请求。不上 Redis。
- 自定义覆盖：纯文本 CIDR 表 `data/custom/*.txt`，每行 `CIDR|区域串`，优先级最高。
- 请求量控制靠**二分收敛**（段内 mid 一致则整段确认），不靠限流堆并发。

### 已完成（阶段 0）
- 旧代码全部归档到 `_legacy/`（含 README 说明可借鉴点与 6 个已知缺陷），已 gitignore。
- 删除根目录 7 个二进制 + `ip2region_20250721_i.xdb`(29MB)。
- `testdata/golden/ip2region_20250721_qqwry.xdb` 留作回归对拍基准。
- 新骨架：`cmd/ip2region`（唯一 main，子命令 fetch/parse/enrich/merge/build/verify/look）+
  `internal/{geo,qqwry,store,provider,enrich,xdbbuild}`；`go mod tidy` 已清空旧依赖。
- `internal/geo` 已实现并可测：`GeoInfo`(6 段 sanitize/parse)、`Segment`、
  `Normalize`(全覆盖无缝隙) / `Apply`(覆盖优先级) / `Compact` / `Validate` / `Find`；7 个测试全绿。
- `Normalize` 重叠语义 = 按 Start 升序"先到先得"；显式优先级走 `Apply`。

## 阶段 1 完成（同日）

### 重大发现：metowolf 版 qqwry.dat 的真实格式
- **字段已用 en dash `–`（U+2013）预先分隔**，省用短名：`中国–福建`、`中国–广东–广州`、
  `美国–加利福尼亚州–圣克拉拉–山景城`；ISP 在 area 串且已规范化（中国电信/BGP多线/Apple…）。
- 不是原版 CZ88 连写格式。regions 包做成双格式：dash 串直接按段填，连写串走后缀链兜底。
- 省短名只补 34 个全称；市/区/镇**保持原样不补后缀**（避免造出"延边市"），形式统一留给 enrich 阶段。
- 港澳台强制 Country=中国；直辖市（`中国–上海–上海`）重复段去重。
- 少量漏分隔脏串（`山东德阳市`、`香港葵涌区`）靠省段二次匹配消化。

### 实测数据（data/qqwry.dat, metowolf 2025-08）
- 151.1 万原始记录 → 133.7 万段（大量单 IP 精度段，如 8.8.8.8），parse 耗时 9.7s
- 中国 4.01 亿 IP（≈9.3% v4 空间），拆不出省 0.60%，无 ISP 6.99%
- 美国段极多（AWS Herndon 等数据中心 IP 细分），境外也拆到州/市/县

### 代码
- internal/qqwry：按 LumaQQ 规范实现 0x01（整体跳转）/0x02（仅国家跳转，地区在 mode+4），
  修复旧实现 0x02 误读；测试用合成 dat 覆盖 4 种记录形态（注意测试数据须先编码成 GBK）
- internal/regions + internal/store(SQLite WAL, modernc.org/sqlite 纯 Go 驱动) + cmd parse/verify/look
- 已提交 2 个 commit（阶段0、阶段1）

## 阶段 2 完成（同日）：xdb 可用，golden 对拍全绿

### 关键发现
- golden xdb（旧流水线产物）的 region 格式 = `国家–省–市–区|组织`（dash 分隔 + 竖线接组织名），
  例如 `中国–山东–济南|教育网/山东女子学院`、`俄罗斯|Akamai节点`。
- **旧 binding searcher 的 SearchByStr 被旧流水线改坏过**：返回前用 replacer 删掉
  `|`、`0`、`中国` —— 连 IP 地址里的 0 都会被删。已恢复官方原样返回。排查时先怀疑
  maker/searcher 索引不一致，实际数据块是好的（矢量索引 512KB=256×256×8，数据块起于 524544）。
- ISP 文本落镇字段问题：qqwry area 串里 `阿里巴巴anycast公共DNS` 等组织名未被旧字典识别。
  已扩充 ispOrgTable（阿里/腾讯/谷歌/Apple/网宿/IDC/机房等），命中后整串进 ISP 字段不归一。
  注意"苹果"会撞北京苹果园/广西平果，只用 "Apple"。

### 实现
- internal/xdbmaker：收编官方 maker+binding searcher（Apache 2.0），去重常量/IndexPolicy，
  补 IterateSegments/CheckSegments，自包含无外部依赖。
- cmd build：段表→源 txt(起止IP|6段region)→官方 maker。133.7 万段 9.6s 出 20.6MB xdb。
- cmd look --xdb 直接查 xdb；cmd verify --golden 5 万随机 IP 对拍：
  **国家一致率 99.99%，省级一致率 100%**（分歧集中在 CloudFlare anycast/IPXO 段，
  是新旧 qqwry 数据版本差异，正好留给百度 enrich）。
- 注意统计口径：中国 IP 只占 v4 空间 ~9.3%，省级一致率必须按"双方均判为中国"的 IP 算。

## 阶段 3/4/5 完成（2026-11-04）

### 百度接口实测补充
- `39.136.55.14` → `"中国 移动"`（只有国家+ISP，无省市）；`8.8.8.8` → `"美国"`。
  所以 enrich 铁律：**只补空、只覆盖更具体的值，绝不清空已有省市**。
- 接口无 AK 无配额，实测 30~60 QPS 稳定。

### enrich（阶段3）
- `regions.ParseLocation` 处理 `广东省广州市 电信` / `北京市海淀区 百度` / `中国 移动` /
  境外纯国家；单字段无空格串先看行政区后缀再判 ISP（否则"广东省广州市电信"会被整体当 ISP）。
- `/24` 去重：19 万中国段 → 11.2 万探测点。**缓存即断点**，重跑零请求，kill 掉也无损。
- 规则：区镇永不改；省市百度非空且不同才改，**改省必须同步改市**（否则留跨省组合）；
  ISP 只补空，两边都有值只记冲突到 `build/enrich-conflicts.tsv`。
- `sameName()` 忽略"市/区/县"后缀差异，避免 qqwry 的"广州" vs 百度"广州市"全表改写。

### refine（阶段4，关键发现）
- **19 万中国段里 18,685 段 > /20，覆盖中国 83% 的地址空间**。单中点探测会把
  一个城市的结论套到几百万 IP 上，这是比 enrich 更大的精度风险。
- 解决：探 起点/中点/终点，三点一致整段确认（1~3 次请求），不一致在 mid 二分递归
  （深度默认 2，最多 4 片）；细分用 `ReplaceSegment`（删+插，单事务）保证连续不重不漏。
- 实测 `1.15.0.0/16` 原标"天津" → 切成 北京/北京/北京/大连。
- 典型纠正：`1.12.0.0/14` qqwry 标"广东广州/腾讯云"，百度实测各地方正宽带 →
  province 改北京，ISP 保留腾讯云（归属方信息比地理位置更有价值）。

### merge（阶段5）
- `data/custom/*.txt`：CIDR 或 起止IP 两种写法 + 6 段区域串；超 6 段直接报错防竖线错位。
- `Apply` → `Compact` → `Validate`；`build --from txt` 直接吃 merge 产物。

### 流水线
parse → enrich（全段，/24 去重）→ refine（大段细分）→ merge（自定义覆盖）→ build → verify。

## 重要修正：云/Anycast 段不能用百度覆盖（2026-11-04）

### 发现过程
1. 换到最新 qqwry（20261028，旧库是 2025-08-06，落后 15 个月）后，
   与 golden 对拍省级一致率从 100% 掉到 **93.31%**。
2. 交叉验证（ip-api）发现 enrich 有对有错：
   - `117.73.42.17` qqwry 标北京、百度标山东济南 → **百度对**
   - `116.243.1.122` qqwry 标广东广州、百度标北京 → **百度错**
3. 规律：错的全是云/CDN/IDC 段（腾讯云/华为云/阿里云…）。
   这类段的 IP 归属于云厂商，但流量落在哪个 PoP 由路由决定，
   **百度探到的是 PoP 城市，不是网段归属地**。

### 修正
- 新增 `regions.IsCloudISP()`（腾讯云/阿里云/华为云/网宿/CloudFlare/Akamai/BGP/IDC/机房…）
- enrich.decide + refine.applyTo 统一口径：**云类段只补空，不覆盖省市**
- 另加一条置信度门槛：百度说换省却给不出市、而原值本来有市 → 整条不动
  （之前会清空市，产出"广东省" + 空市这种残废结果）

### 进一步结论：默认改成"只补空"
40 个被改样本 × ipwho.is 交叉验证：**新值 82.1%、旧值 82.1%** —— 完全打平。
百度与 qqwry 是同一量级的噪声源，覆盖等于抛硬币。
最终策略：`enrich` 默认**只补空**，覆盖需 `-override`。
真正可量化的收益全在填空：
- 省 95.84% → 99.08%，市 81.18% → 91.54%，ISP 85.00% → 89.56%
- 区县/乡镇 不变（4.67%/15.01%，数据源本身就没有）

### verify 对拍口径修正
原来把"旧库为空、新库补上"也算成不一致。改成三分类后：
一致 95.19% + 改进 3.49% + 真冲突 1.31%。

### 影响
- 保护 3,948 段 / 3,489 万 IP（中国空间 8.7%）不被误改

### 经验
- ip-api 不能当中国 IP 的裁判：大量返回"北京市金融街"（它自己的机房）
- 判断数据源可信度要看**失败模式**，不是只看一致率数字



## 接入运营商网段表 ispip.m27.tech（2026-11-04）

### 数据
- 21 个页面（chinatelecom/unicom/cmcc/tencent/alisoft/huawei...），每页纯 CIDR 列表
- 来源 APNIC 分配记录 + whois，每日生成；官方注明"脚本自动生成，难免有错漏"
- 排除"其他"桶后覆盖 7.16% 全域；**对中国段覆盖 95.51%**
- 和百度本质区别：这是**分配归属**，不是探测点位置，不受 anycast/PoP 影响

### 实现
- `internal/ispip`：页面名→运营商映射、优先级 sweep 成不重叠索引、二分开区间查询
- 优先级：云厂商/IDC(40) > 教育网/科技网/广电(20) > 基础运营商(10)
  必须这样，否则 `1.12.0.0/14` 会被电信列表里同段的条目抢走（同一段在两个列表里都出现）
- 不收录 othernet/hongkong/macau/taiwan：地域兜底桶，不是运营商
- `enrich -ispip`：先按网段表定 ISP（补空/纠正云厂商），百度只负责剩余填空
- `fetch` 顺便下载这 21 个页面到 data/ispip/

### 两个 bug（都是被数据打出来的）
1. **uint32 溢出**：`(seg.Start + seg.End) / 2` 在起点 >= 128.0.0.0 时溢出，
   一半的段被静默跳过（只改了 800 段）。改 uint64 后变 1776 段。
   教训：凡是对 IP 做算术，一律先转 uint64。
2. **港澳台运营商误归一**：`ispTable` 里 `电信 → 中国电信` 是子串匹配，
   把"中华电信"归成"中国电信"，影响 4,596 段 / 1,903 万 IP。
   修法：中华电信/远传/台湾固网/香港电讯/和记/数码通等排在"电信"之前。

### 结果
- ISP 覆盖率 89.56% → 90.48%（IP 加权的中国段）
- 剩余空 ISP 主要是香港(5,276 段)/台湾(3,166 段)，网段表只有地域桶，填不了
- 与 qqwry ISP 一致率 91.1%，分歧里 284 段"长城宽带→腾讯云"是真实转售关系

## 接入 GeoCN 补区县（2026-11-04）

### 数据
- ljxi/GeoCN，MMDB 格式，8.6MB，111.3 万 IPv4 网段（+6.9 万 IPv6）
- 字段只有 2 个：`division_code`（uint64，国标 6 位行政区划编码）+ `isp`（7 种粗标签）
- 编码表用同仓库 `data/full.txt`（AreaCity）：`110101<TAB>东城区`
- 来源"二分算法扫描公开 API"，随缘更新（当前 2026-04）
- 粒度分布（IP 加权）：区县 54.1% / 市级 29.0% / 省级 16.9%，共覆盖 3.45 亿 IP

### 为什么值得接
**区县是唯一缺口**：qqwry 只有 4.67%，百度/网段表都到不了。GeoCN 能把它推到 40.67%。
省市不用它（省 96.4% 一致、市 81% 一致，都低于 qqwry 自身稳定性）。

### 合并规则（核心设计）
- 只补空，绝不覆盖已有区县。qywry 已有区县的 36,493 段与 GeoCN 不同，无证据谁更准
- **省市必须自洽**：GeoCN 的省/市与我们不一致 → 整条放弃（10,326 段）。
  否则产出"吉林省长春市|玄武区"这种错位数据
- 云/CDN 段跳过：GeoCN 同样是扫 API 的，云段给 PoP 城市
- 区县填了以后不必再管镇：GeoCN 没有镇级

### 实现
- `internal/geocn`：maxminddb-golang v2（`db.Lookup(netip.Addr)` → `Result.Decode`）
  + 编码翻译（前 2 位省、前 4 位市、6 位区县；末四位 0000 表示只到省）
- `enrich -geocn data/geocn/GeoCN.mmdb`，在 ispip 之后、百度之前执行
- `store.SegmentUpdate` 增加 County/Town 可空字段

### 结果
- 区县 4.67% → 40.67%（1885 万 → 1.64 亿 IP）
- xdb 段数 141 万 → 138 万（区县补齐后相邻段相同，Compact 合得更多）
- 对拍：一致 95.99% + 改进 3.01% + 真冲突 1.00%

### 仍未解决的
- 镇级：没有任何源提供（qqwry 偶尔有 area 字段），只能靠自定义覆盖
- 剩余 59% 区县空缺：GeoCN 本身只到市级，或省市不一致主动放弃
